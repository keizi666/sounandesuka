# 16 エディター: エリア・地形・登山道・地点・環境

コードは `src/editor/geo/`（通信と変換）と `src/editor/panels/`（UI）。変換結果は既存の `MapDef` 形式にそろえ、`src/sim` 側は「手続き生成の地形」と「実在の高さマップ」の違いを意識しない。

## 1. 投影と座標

- 箱庭の座標は従来どおりメートル（`x` 東、`z` 南）。原点 = エリア中心 `(lat0, lon0)`。
- 変換は局所接平面（正距円筒の近似。12 km 四方での誤差は数 m で十分）:

```
R = 6378137
x =  (lon - lon0) * π/180 * R * cos(lat0)
z = -(lat - lat0) * π/180 * R
```

- 逆変換も用意（`geo/projection.ts`）。`MapDef.geo = { centerLat, centerLon, projection: "local-tangent" }`。
- タイル座標（Web メルカトル）⇔ 緯度経度は標準式。`geo/tiles.ts`。

## 2. 2D 地図ビュー（`editor/map/TileMapView.ts`）

自作の Canvas2D、または確認のうえ地図ライブラリを使う（CLAUDE.md「依存の追加」）。どちらでも以下の機能を満たすこと。

- パン（ドラッグ）、ズーム（ホイール・ピンチ、z 10〜17）、タイルのメモリキャッシュ（LRU 400 枚）。
- 背景の切替: 標準地図（`std`）/ 淡色（`pale`）/ 写真（`seamlessphoto`）/ 陰影（`hillshademap` を半透明で重ねる）。
- 右下に出典「地理院タイル」（リンク）を常時表示。
- 上にレイヤーを重ねる仕組み（`MapLayer` インターフェース: `draw(ctx, view)`, `hitTest(px, py)`）。登山道、地点、危険箇所、箱庭範囲、雷雲の進路、植生・電波の塗り、計画ルート、試走の軌跡がそれぞれレイヤー。
- 箱庭ができた後は、陰影の代わりに **自前の高さマップから描いた陰影段彩**（Canvas に 1 回描いてキャッシュ）も選べる。

## 3. エリア（タブ 1）

### 3.1 範囲の指定

- 地名検索は入れない（外部サービスを増やさない）。代わりに緯度経度の直接入力と、地図のパン・ズームで探す。
- 「範囲を置く」で地図中央に正方形の枠を出し、ドラッグで移動、角で大きさを変える（北が上で固定、回転なし）。
- 大きさと解像度:

| 一辺 | 解像度（頂点数） | セル |
|---|---|---|
| 2.0〜4.0 km | 257 | 8〜16 m |
| 4.0〜6.0 km | 385 | 10〜16 m |
| 6.0〜12.3 km | 513 | 12〜24 m |

  一辺はセルが整数メートルになるよう丸める（例: 6 km → 513 頂点、セル 12 m → 6,144 m）。

### 3.2 標高の取得（`geo/dem.ts`）

1. 範囲を覆う z14 の `dem_png` タイルを列挙（6 km 四方で概ね 9〜16 枚）。同時 4 本で取得。
2. 「詳細（DEM5A を優先）」オプション時は z15 の `dem5a_png` も試し、取れた画素はそちらを使う（404 のタイルは z14 で補う）。
3. 画素の標高: `x = R·2^16 + G·2^8 + B`; `x < 2^23` なら `h = x·0.01`、`x = 2^23`（(128,0,0)）は無効、`x > 2^23` なら `h = (x − 2^24)·0.01`。
4. 箱庭グリッドの各頂点の緯度経度を求め、タイル画素を双線形補間でサンプル。無効値は周囲 8 近傍の有効値の平均で埋め、それでも無効なら（海・湖など）範囲内の最小標高を入れて警告する。
5. 頂点数が多いので、デコードは Worker（`workers/dem.worker.ts`）で行う。
6. 結果: `Float32Array` → `MapDef.terrain`:

```jsonc
"terrain": {
  "type": "heightmap",
  "encoding": "u16-base64",
  "minElevM": 1452.3, "maxElevM": 2763.0,
  "baseElevation": 1400,          // 台座の上面（minElevM − 余白、50 m 単位で切り下げ）
  "source": { "dem": "DEM10B", "zoom": 14, "fetchedAt": "2026-11-17T08:00:00+09:00" },
  "data": "…"                     // Uint16 LE、h = min + v / 65535 * (max - min)
}
```

量子化誤差は 1,300 m の起伏で 2 cm 程度で問題ない。

### 3.3 地形の後処理（任意）

- **平滑化**: 3×3 ガウシアン 0〜3 回（DEM10B の段差ノイズ対策。既定 1 回）。
- **鉛直誇張の推奨値**: 起伏 / 一辺 が小さい（なだらかな）エリアでは 1.2〜1.5 を提案（描画のみ）。
- 派生レイヤーは `docs/04` §4 と同じ処理を、セル寸法 `cellM = size / (resolution − 1)` で計算（`derive.ts` を一般化する）。

## 4. 登山道（タブ 2）

### 4.1 OpenStreetMap から取り込む（`geo/overpass.ts`）

エリアの外接矩形で 1 回だけ問い合わせる:

```
[out:json][timeout:60];
(
  way["highway"~"^(path|footway|track|steps|bridleway)$"]({{bbox}});
  node["natural"="peak"]({{bbox}});
  node["natural"="saddle"]({{bbox}});
  node["tourism"~"^(alpine_hut|wilderness_hut)$"]({{bbox}});
  way["tourism"~"^(alpine_hut|wilderness_hut)$"]({{bbox}});
  node["amenity"="shelter"]({{bbox}});
  node["waterway"="waterfall"]({{bbox}});
  node["information"="guidepost"]({{bbox}});
  node["highway"="trailhead"]({{bbox}});
);
out geom tags;
```

**グラフへの変換**:

1. way を頂点列にし、複数の way が共有する OSM ノード、way の端点、取り込んだ地点（山頂・小屋など）から 25 m 以内の点を **分岐点** とする。
2. 分岐点で way を分割してエッジにする。2 本の way が分岐点なしでつながっている場合は 1 本に結合。
3. エリア外にはみ出る部分は境界で切り、境界上に `trailhead` 候補ノードを作る（作者が確認）。
4. 頂点を 10 m 間隔で再サンプル。`smooth: false`（実在の形状をそのまま使い、Catmull-Rom をかけない）、`sinuosity: 1.0`。
5. 属性の自動設定:

| OSM タグ | 設定 |
|---|---|
| `sac_scale=hiking` | class T1 |
| `sac_scale=mountain_hiking` | T2 |
| `sac_scale=demanding_mountain_hiking` 以上 | T3 |
| `sac_scale` なし | 平均傾斜 < 15° で T1、< 25° で T2、それ以上 T3 |
| `trail_visibility=excellent/good` | markers 0.9 / 0.75 |
| `trail_visibility=intermediate` | markers 0.5、drift 0.03 |
| `trail_visibility=bad/horrible/no` | markers 0.2、drift 0.06（廃道候補として印を付ける） |
| `highway=track` | T1、markers 0.8（林道） |
| `abandoned` / `disused` 系 | `kind: "false"` 候補 |

6. 地点: `natural=peak`→`peak`、`saddle`→`saddle`、`alpine_hut`→`hut`（`staffed`）、`wilderness_hut` と `amenity=shelter`→`shelter`（`emergency`）、`highway=trailhead`→`trailhead`、`waterway=waterfall`→危険箇所 `waterfall`（半径 40 m）。名前は `name:ja` → `name` の順。標高は DEM から（OSM の `ele` は表示のみ）。
7. 取り込み直後は **すべて「下書き」状態**（地図上で破線）。作者が使う道を選んで「確定」する。使わない道は一括で除外できる（「計画ルートから 1 km 以上離れた道を除外」ボタンなど）。

### 4.2 GPX から取り込む（`geo/gpx.ts`）

- `<trk><trkseg><trkpt lat lon><ele>` と `<wpt>` を `DOMParser` で読む。
- 用途を選ぶ: 「登山道として追加」（既存エッジと 15 m 以内で重なる部分は既存を優先し、重ならない部分だけ新しいエッジ）／「計画ルートとして使う」（既存グラフにマップマッチングしてノード列を得る）／「偽の道（迷った軌跡）として追加」。
- `<wpt>` は地点候補として出す。

### 4.3 手描き

- クリックで頂点を置き、既存ノードの 20 m 以内ならスナップ。ダブルクリックで終了。
- 頂点のドラッグ、挿入（線上をクリック）、削除（Alt+クリック）。
- エッジの分割（ノード挿入）、2 エッジの結合、向きの反転。
- 描いた線は DEM に沿って標高を付ける。描画中に区間ごとの傾斜をツールチップ表示し、38° 超（偽の道は 50° 超）を赤で示す。

### 4.4 エッジのインスペクタ

名前、種類（trail / false）、class、markers、drift、`fadeOutM`（false のみ）、`attractiveness`（false のみ）、**標準コースタイム**（順・逆、分）。

コースタイムを入れると、標準登山者のシミュレーション時間と比べ、ずれを補正する係数 `paceAdj`（0.6〜1.4）を自動提案する（`docs/07` §1.1 の速度に乗算）。地図やガイドブックの数字を写して入力する想定。

### 4.5 分岐の紛らわしさ（confusers）

- 自動提案: 分岐ノードで、2 本のエッジの出ていく角度の差が 40° 未満、または一方が false / markers ≤ 0.3 のとき候補にする。基本値 `ambiguity = 0.15 + 0.4 × (1 − 角度差/40°)`（false が絡めば +0.2）。
- インスペクタでノードを選ぶと、出ていくエッジの組み合わせ表（行: 進むつもりの道、列: 間違えて入る道）で値を編集できる。

## 5. 地点と危険箇所（タブ 3）

- ノード: 名前、種類、小屋の種類（staffed / emergency）、営業中か（シナリオの季節で変えたいことが多いので、シナリオ側 `nodeOverrides: { "HUT_X": { "open": false } }` でも上書き可）。
- 危険箇所: 鎖場（エッジ上の区間をドラッグで指定）、滝（点＋半径）、落石帯（区間）、保護範囲（点＋半径）。
- 崖は傾斜から自動で決まる。地図上に傾斜 50° 超を赤で重ねて確認できる。
- ノード ID は自動採番（`N001` 形式）だが、作者が読みやすい ID（`HUT_ENZAN` など）に変えられる。変えると参照（シナリオの条件・ルート）も一括で書き換える。

## 6. 環境（タブ 4）

### 6.1 植生

- 標高による自動分類（`docs/04` §4）。パラメータ: 森林限界（例: 北アルプス 2,500 m、八ヶ岳 2,400 m、東北 1,600 m 前後）、広葉樹林の上限、ハイマツ帯の幅。
- エリア選択時に緯度から初期値を提案する（北緯 36° で森林限界 2,500 m、1° 北上ごとに −200 m、を目安）。作者が必ず確認する。
- **塗り直し**: ブラシ（半径 20〜200 m）で植生クラスを塗る。結果は `vegetation.overrides`（Uint8 グリッド、0 = 自動、1〜7 = クラス+1）を RLE + base64 で保存。

### 6.2 電波

- 実在のキャリアのエリアマップはデータとして使えないため、**近似**として扱う（UI に明記）。
- 基地局ピンを置く（箱庭の外にも置ける。標高・アンテナ高・到達距離を指定）。初期配置として、エリア周辺の最も低い方角の 8 km 先に 1 局を提案する。
- 塗り: 「電波あり」「圏外」をブラシで上書き（山頂で通じた・小屋で通じない等、作者の経験を反映）。`radio.paint`（Int8 グリッド、0 = 自動、+1 = 強制あり、−1 = 強制圏外）。
- 計算結果を地図に重ねて確認。

### 6.3 地形の確認ビュー

- 2D: 傾斜、植生、電波、風の露出（TPI）、空の見通しの切替表示。
- 3D: 本番の `view/` で箱庭を表示（登山道・地点つき）。

## 7. 検証（地理データ）

`npm run validate` と同じ検証をエディター内で常時実行し、地図上の該当位置にマーカーを出す。

| 種類 | 内容 |
|---|---|
| エラー | エッジの端がノードにつながっていない、ルートの隣接ノード間にエッジがない、ノードがエリア外、ID 重複 |
| 警告 | 正規の道の傾斜 38° 超、孤立したノード、コースタイムとシミュレーションのずれ ±25% 超、下山口ノード（trailhead）がない、小屋がエリアに 1 つもない（ビバーク一択になる） |
| 情報 | 取り込んだがまだ確定していない道の数 |

## 8. スケルトンマップの結合

座標を持たない「骨組みだけのマップ」（`MapDef` の `skeleton: true`、ノードに `osmName` と概略の標高だけがある）を読み込み、実地形に結び付ける機能。史実シナリオの配布に使う（座標データや OSM 由来データを含めずに配布できる）。

1. スケルトンを読み込むと、`areaHint`（エリアの説明と目安の大きさ）を表示し、作者が地図上で範囲を置く。
2. 標高取得と OSM 取り込み（§3, §4）を行う。
3. 各スケルトンノードについて、`osmName` と名前が一致（`name:ja` / `name` の部分一致、ひらがな・カタカナ同一視）する OSM 地点を候補に出す。候補が複数なら `expectedElevM` に近い順。作者が確定する。候補がなければ地図上をクリックして置く。
4. スケルトンのエッジは、結び付いた両端ノード間を OSM の登山道グラフ上の最短経路でたどってポリライン化する。`via`（経由する OSM 地点名）があればそこを通す。
5. ID はスケルトンのものを保つ（シナリオの参照が壊れない）。
6. 結合後、エッジの `courseTimeMin`（スケルトンに記載があれば）で `paceAdj` を提案する。
